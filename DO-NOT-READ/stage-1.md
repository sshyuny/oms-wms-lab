# 단계 1 — 주문이 몰리면 재고가 음수가 됨

> 단계 1 작업이 끝난 뒤에 연다. 리뷰어(AI)는 사용자가 이 단계의 리뷰·힌트·공개를 요청했을 때만 읽는다.

## 심어 둔 원인
- 위치: `StockService.decrease` → `StockRepository.decreaseQuantity`
- 재고를 조회해서 `quantity < 요청수량`인지 검사한 뒤, 차감은 별도 쿼리 `update stock set quantity = quantity - :q`로 한다.
- 검사와 차감 사이에 락이 없다. 동시 요청이 같은 수량을 읽고 둘 다 검사를 통과하면, 차감 쿼리 자체는 원자적이라 값이 그대로 빠져 음수가 된다.
- "차감을 원자적 update로 했으니 안전하다"는 착각을 노린 함정이다. 엔티티 setter로 차감했다면 음수 대신 갱신 손실(lost update)로 나타났을 것이다.

## 재현 방법 예시
- 재고 1개, 스레드 2~10개가 동시에 주문 생성 (`ExecutorService` + `CountDownLatch`).
- 테스트 메서드에 `@Transactional`을 붙이면 동시성이 재현되지 않는다. 각 요청이 각자 커밋돼야 한다.
- 기대: 성공 주문 수 ≤ 재고, 최종 재고 ≥ 0.

## 해법 방향 (참고, 사용자 해법이 달라도 됨)
- 조건부 update: `... set quantity = quantity - :q where product_id = :id and quantity >= :q` + 영향받은 행 수가 0이면 재고 부족
- 비관적 락: `select ... for update`로 조회 후 검사·차감
- 낙관적 락: `@Version` + 재시도

## 리뷰 체크포인트
- 여러 상품을 담은 주문에서 비관적 락을 쓰면 상품 잠금 순서가 요청마다 달라 데드락 가능 → productId 정렬 등
- 한 주문에 같은 상품이 두 줄 들어오는 경우 (현재 검사는 영속성 컨텍스트의 오래된 값을 볼 수 있음)
- 재현 테스트가 실제로 동시에 실행되는지, 실패 전에 한 번은 빨간불을 봤는지

## 실제 해결 기록 (PR #3)

### 사용한 방법
- 조건부 update: `update Stock s set s.quantity = s.quantity - :quantity where s.productId = :productId and s.quantity - :quantity >= 0`
- 영향받은 행 수가 1이 아니면 `OUT_OF_STOCK`으로 거절한다. 주문 트랜잭션 전체가 롤백된다.
- base에 있던 조회 후 사전 검사는 빠른 실패용으로 남겼다. 정확성은 update의 WHERE 절이 보장한다.

### 위 해법 방향과 다른 점
- 해법 방향의 첫 번째(조건부 update)와 같다. 조건을 `quantity >= :q`가 아니라 `quantity - :q >= 0`으로 썼을 뿐 의미는 같다.
- 처음에는 읽었던 값과 같을 때만 차감하는 조건(`where quantity = :beforeQuantity`)을 썼다. 사실상 재시도 없는 낙관적 락이라, 초과 판매는 막았지만 다른 요청이 먼저 바꾸면 재고가 남아 있어도 거절되는 과소 판매가 생겼다(스레드 40개 기준 재고 6 남음, 36건 거절). 위 낙관적 락 항목에 "+ 재시도"가 붙은 이유다.
- 재현 테스트는 재고 10개, 스레드 100개로 했고, 기대를 "최종 재고 ≥ 0"보다 엄격한 "최종 재고 == 0"으로 두었다. 이 단언 덕분에 첫 시도의 과소 판매를 잡았다. "≥ 0"이었다면 첫 시도도 통과했다.
- 원인 진단 과정에서 "UPDATE가 행 락을 잡으니 안전하다"는 함정에 실제로 걸렸고, 격리 수준 상향(SERIALIZABLE)과 JPA 1차 캐시도 의심했다가 버렸다.

### 리뷰 체크포인트 상태
- **여러 상품 주문의 데드락: 여전히 걸림.** 비관적 락이 아니어도 조건부 update가 행 락을 커밋까지 쥐므로, 주문마다 상품 차감 순서가 다르면 데드락이 날 수 있다. MySQL이 한쪽을 롤백하지만 그 예외를 따로 처리하지 않아 500으로 나갈 가능성이 크다. PR의 "남은 위험"에만 적고 해결하지 않았다(productId 정렬 등).
- **한 주문에 같은 상품 두 줄: 결과는 막히지만 검사는 여전히 오래된 값을 봄.** 두 번째 줄의 사전 검사는 영속성 컨텍스트의 차감 전 값을 봐서 잘못 통과할 수 있다. 다만 update의 WHERE 절이 DB 최신 값으로 다시 판단하므로 0행이 되어 `OUT_OF_STOCK`으로 거절된다. 코드 흐름으로 추론한 것이고 테스트로 확인하지 않았다.
- **재현 테스트의 동시 실행·빨간불: 해소.** 테스트에 `@Transactional`이 없고, base에서 재고 -9, 주문 19건(스레드 40개)으로 실패를 확인했다.
