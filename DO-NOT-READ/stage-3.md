# 단계 3 — 출고 쪽이 느려지거나 실패하면 결제 완료까지 같이 실패함

> 단계 3 작업이 끝난 뒤에 연다. 리뷰어(AI)는 사용자가 이 단계의 리뷰·힌트·공개를 요청했을 때만 읽는다.

## 심어 둔 원인
- 위치: `PaymentService.approve`가 하나의 `@Transactional` 안에서 순서대로 한다.
  1. `FakePgClient.approve` — 외부 PG 승인 (DB 롤백과 무관)
  2. `Payment` 저장
  3. 주문 `PAID` 변경
  4. `ShipmentService.createShipment` — 창고가 `SUSPENDED`면 `WAREHOUSE_SUSPENDED` 예외
- 4에서 예외가 나면 2·3은 롤백되지만 1은 그대로 남는다. 고객은 결제 실패 응답(409)을 받았는데 PG에는 승인 내역이 있다(돈이 빠짐). 주문은 `PENDING_PAYMENT`로 남는다.
- 재현: `PATCH /api/warehouses/1/status {"status":"SUSPENDED"}` 후 결제 → 409, `FakePgClient`에 `APPROVED` 거래가 남음, `payment` 테이블은 비어 있음.
- 반대 방향 결합도 있다: `ShipmentService.ship`이 `OrderRepository`로 주문 상태를 직접 바꾼다.
- 외부 PG 호출이 DB 트랜잭션 안에 있어 PG가 느리면 DB 커넥션을 오래 잡는다.

## 해법 방향 (참고)
- 결제 확정(결제 저장 + 주문 PAID)과 출고지시 생성을 트랜잭션으로 분리
- 결제 트랜잭션 안에서 아웃박스 테이블에 "결제 완료" 이벤트를 기록하고, 릴레이가 출고지시를 생성 (창고가 재개되면 재시도)
- 출고지시 생성은 멱등하게 (`shipment.order_id` unique를 이용하거나 이벤트 ID 기록)
- 주문·창고 모듈 경계 정리 (주문이 창고 내부 클래스를 직접 부르지 않게)

## 리뷰 체크포인트
- 이벤트 중복 전달 시 출고지시가 두 번 생기지 않는지
- 출고 완료 → 주문 상태 갱신도 같은 방식으로 분리했는지
- PG 승인 후 DB 저장 실패 시 보상(PG 취소) 처리

## 실제 해결 기록

현재까지의 구현과 리뷰 기록이며, 단계 완료·PR merge 전 상태다.

### 사용한 방법

- 출고 실패를 결제 흐름에서 처리하고, 두 작업의 트랜잭션을 분리해 결제를 유지했다.
  - `PaymentService.approve()`에서 `catch (Exception e)`로 출고 예외를 처리하고 주문 ID와 스택 트레이스를 기록했다.
  - `ShipmentService.createShipment()`에 `REQUIRES_NEW`를 적용했다.
- 결제 완료 후 출고가 누락된 주문을 찾아 복구하는 내부 API를 만들었다. 외부에서 주기적으로 호출하는 용도이며, 호출 스케줄러는 구현하지 않았다.
  - `POST /internal/shipments/create`에서 `PAID`이면서 출고가 없는 주문을 조회해 출고지시를 생성한다.
  - 배치·Lambda가 이 API를 주기적으로 호출하는 방식을 구상했다.
- 실제 창고 중지 상황으로 테스트해 결제 롤백 문제를 재현하고, 분리 후 결제 성공을 확인했다.
  - `ShipmentService` mock과 테스트의 `@Transactional`을 제거하고 창고를 `SUSPENDED`로 변경했다.
  - 기존 코드의 `UnexpectedRollbackException`을 확인했고, 트랜잭션 분리 후 결제 응답·PG 승인·주문 `PAID` 상태 검증이 통과했다.

### 참고 해법과 다른 점

- 실패를 분리하고 재시도한다는 방향은 같다. 다만 현재는 결제 요청 안에서 출고를 기다리므로 지연은 분리되지 않았다.
  - `PaymentService.approve()`가 `createShipment()`를 동기 호출한다. 예외를 잡아도 호출이 끝나야 결제 커밋으로 진행한다.
- 참고 해법은 결제 확정과 함께 처리할 이벤트를 저장한다. 현재는 주문과 출고 상태를 비교해 복구 대상을 찾는다.
  - 아웃박스 이벤트와 릴레이 대신 `PAID` 주문과 출고 테이블을 조인해 출고가 없는 주문을 조회한다.
- 출고가 결제보다 먼저 확정될 수 있어, 결제 실패 시 출고만 남는 위험이 있다.
  - 출고의 `REQUIRES_NEW` 트랜잭션이 먼저 커밋된다. 이후 외부 결제 트랜잭션의 커밋이 실패해도 출고는 롤백되지 않는다.
- 복구 작업은 주문별로 독립 처리되지 않아, 한 건의 실패가 해당 호출 전체에 영향을 준다.
  - `createForPaidOrder()`에서 같은 클래스의 `createShipment()`를 호출하므로 `REQUIRES_NEW`가 적용되지 않는다. 복구 호출 전체가 하나의 트랜잭션이다.

### 리뷰 체크포인트 상태

- 해소: 창고 중지로 발생한 출고 실패가 결제까지 롤백시키는 문제. 실제 서비스로 검증했다.
  - `PaymentShipmentFailureApiTest`에서 실제 `WAREHOUSE_SUSPENDED` 예외가 발생해도 결제 API가 `201`을 반환하고 주문이 `PAID`로 유지되는 것을 확인했다.
- 여전히 걸림: 중복 복구 요청의 안전성. 중복 저장은 제한하지만 동시 요청이 실패할 수 있으며, 동시 실행은 검증하지 않았다.
  - `shipment.order_id` 유일 제약조건은 있지만, 두 복구 호출이 같은 주문을 조회하면 생성 시 충돌해 해당 호출 전체가 롤백될 수 있다.
  - 현재 중복 테스트는 출고가 이미 존재하는 주문을 제외하는 경우만 검증한다.
- 여전히 걸림: 결제 확정 이후 출고 처리와 출고 지연의 분리.
  - 결제 중 동기 출고 호출이 남아 있고, 출고 커밋 후 결제 커밋이 실패하는 상황과 출고 지연은 검증하지 않았다.
- 여전히 걸림: 출고 완료에 따른 주문 상태 갱신의 분리.
  - `ShipmentService.ship()`이 `OrderRepository`로 주문 상태를 직접 `SHIPPED`로 변경한다.
- 여전히 걸림: PG 승인 후 DB 저장 실패 시 승인 취소 보상.
  - `FakePgClient.approve()` 이후 결제 저장·커밋에 실패해도 PG 승인을 취소하는 처리가 없다.
- 여전히 걸림: 출고가 없는 결제 완료 주문의 취소·환불.
  - `OrderService.cancelOrder()`는 `PAID` 주문에 출고가 없으면 `SHIPMENT_NOT_FOUND`로 종료해 환불까지 진행하지 못한다.

이전 전체 테스트 19개와 이후 변경한 결제 패키지 테스트는 통과했다. 남은 위험을 검증하는 테스트는 추가하지 않았다.
