# 3단계 해결 시도와 리뷰

## 1. 결제 중 출고 예외를 try-catch로 처리

출고 생성에서 발생한 예외를 잡고 로그를 남겨 결제를 계속 진행하도록 했다.

문제점:

- [x] 출고 예외로 결제 트랜잭션도 rollback-only가 되는 문제 → `REQUIRES_NEW`로 출고 트랜잭션을 분리했다.
  - [ ] `REQUIRES_NEW`로 출고가 결제보다 먼저 커밋된다. 이후 결제 커밋이 실패하면 출고는 존재하지만 주문은 미결제인 상태가 남을 수 있다.
- [ ] 출고 호출이 끝날 때까지 기다리므로 결제 지연은 해결되지 않는다.
- [x] `BusinessException` 외의 예외가 전파되는 문제 → `catch (Exception e)`로 처리 범위를 넓혔다.
- [x] mock이 실제 롤백 동작을 가리는 문제 → mock과 테스트의 `@Transactional`을 제거하고 실제 창고 중지 상황으로 검증했다.
- [x] 실패 로그에 예외 정보가 없는 문제 → 로그에 예외와 스택 트레이스를 남겼다.

## 2. 누락 출고를 생성하는 내부 엔드포인트 추가

결제 완료 상태이면서 출고가 없는 주문을 조회해 출고지시를 생성한다. 배치나 Lambda가 주기적으로 호출하는 용도를 의도했다. 호출 스케줄러는 구현하지 않았다.

문제점:

- [ ] 복구 호출이 겹치면 같은 주문을 동시에 처리해 유일 제약조건에 충돌할 수 있다. 전체가 하나의 트랜잭션이므로 해당 호출의 다른 출고 생성도 롤백된다.
- [ ] 기존 중복 테스트는 출고가 이미 존재하는 경우만 검증하며, 동시 호출은 검증하지 않는다.
- [ ] 결제 성공·출고 없음 상태가 생기면, 기존 주문 취소 로직이 `SHIPMENT_NOT_FOUND`로 실패해 복구 전까지 취소·환불이 막힌다.

## 검증 상태

이전 전체 테스트 19개는 통과했다. 이후 변경한 결제 패키지 테스트도 통과했으며, 실제 창고 중지 상태에서 결제가 성공하는 것을 확인했다. 일반 예외, 결제 커밋 실패, 출고 지연, 복구 호출 전 주문 취소, 복구 동시 호출은 검증하지 않았다.
